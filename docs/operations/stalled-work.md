# 停滞与资源排查

## 先确定影响范围

从用户可见的问题开始，记录发生时间、Track 或会话标识、最后成功操作以及期望发生的下一步。按“整个实例不可达 → 某个 Track 无进展 → 单次执行或资源未释放”逐层缩小范围。

| 现象 | 首先读取 | 需要确认 |
| --- | --- | --- |
| 页面或接口不可达 | 服务管理器日志、neige-app 的 `/health` 与带鉴权的 `/status` | 管理进程是否存活，子进程是否正在启动或重复退出 |
| 能访问，但状态异常 | `/api/version`、当前启动/恢复状态、最近部署记录 | 正在运行的版本，是否处于恢复过程，以及观测是否新鲜 |
| 某 Track 不推进 | 页面任务/会话状态、可用的 `neige_track_status` 及相关状态工具 | 正常等待用户、等待依赖、资源占用、执行中或明确失败 |
| 请求停止后仍未结束 | 精确 session/attempt 的停止请求与后续事件 | 请求是否被接收，是否已有退出或结算证据，结果是否仍未知 |
| 任务结束后资源还在 | 清理候选、租约归属和资源台账 | 当前 owner、宽限期、是否已有后继执行、最近清理结果 |

实际地址与鉴权从实例配置获取。管理接口的调用例子见 [部署指南](../deploy-and-upgrade.md)。

## 沿同一次执行查证据

从 Track 找到相关任务及 attempt，再查它绑定的会话、执行器和资源。重试后这些身份可能改变，使用已有状态接口和归属规则确认关联。

收集最后进展、停止或超时请求、任务结算与资源清理的时间点。报告读取失败和事件分页未结束都意味着证据不完整。仅靠“多久没更新”不足以确定卡住，需要结合该状态原本期待的下一步。

有些等待由任务、租约或未完成交付共同造成。优先使用调度器提供的等待原因；数据库排查遵循 [只读读取说明](database.md)。

## 分开看资源结果

- **遗留会话或执行器**。核对任务终态、活跃后继任务和清理宽限期，查看清理器是否已将其列为候选。
- **仍持有的租约**。确认租约所属的具体 attempt、当前释放阶段及原 owner 的结算结果。旧 attempt 的清理不能关联到新的执行。
- **退役工作区**。按台账的退役原因判断。策略保留的目录继续占用磁盘，维护方式见 [退役策略](../workspace-retirement.md)。
- **未知结果**。缺失退出确认或归属证据时保留未知状态，继续收集该次执行的证据。

## 交接和恢复

先形成一条可复查的记录：目标实例、运行版本、影响对象、最后进展、当前等待或错误、证据链接、已尝试操作和结果。

根据实际问题选择既有的恢复、重启、回滚或离线维护流程。执行前确认目标身份与授权，执行后再次读取实例和相关对象状态。升级及恢复条件统一以 [部署与升级指南](../deploy-and-upgrade.md) 为准。
