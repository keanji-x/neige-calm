# Workspace provider execution environments (S4 protocol)

Status: proposed L2 implementation protocol for #2666, revised after the first
two independent reviews; fresh dual review is required. This changes the S4 architecture in [track-workspace.md](track-workspace.md),
not S1 behavior. It enables no view and claims no provider qualification. S2a
identity/ticket/control contracts and S3 source/lifecycle contracts are prerequisites.
Types below are required implementation contracts, not existing Rust APIs.

## Decision and acceptance

For a view, run the entire provider service inside the workspace execution
namespace. The provider owns an isolated runtime per authorized workspace
binding, resource generation and execution instance. Codex uses an app-server
in that scope with its official local execution tools. The initial profile does
not register a remote exec-server or reuse the worktree shared app-server.
Sharing an explicitly authorized inference account or transport does not mean
sharing an app-server process, mutable state, trust decisions or control socket.
View workers use the managed observation/input console specified below, rather
than a native CLI connected directly to app-server. Core worker interaction is
preserved; the native TUI presentation is an explicit view-product change.

Kernel resolves authority, admission, source evidence and lifecycle. Workspace
implements namespace/filesystem/process mechanisms; provider owns protocol and
qualification. Kernel consumes typed capabilities and `ViewSupport`, never a
Codex/Claude/application-name condition. S4 introduces no second workspace,
task scheduler, occupancy policy, candidate ledger or destruction service.

Acceptance is the production start/turn/control/resume/restart/recovery path
using this scope, with all project reads in its view, independent mutable state,
positive descendant drain, and old-capability rejection. A protocol stub or the
research experiments alone cannot authorize `Supported`. An unqualified profile
returns `Unsupported(reason)` before launch; a failed ready runtime returns a
typed unavailable/recovery error, never a local/shared-process fallback.

## Evidence that changes the parent architecture

`1748767b230ebfc3d4ab7e4e254920d0c0ad9691fd8c11f190e7d44511a4a92e`.

Independent homes and two synthetic Git repositories occupied the same absolute

## Identity and ownership

The provider runtime key is a required tuple, with opaque IDs, not a path:

| Part | Owner and meaning |
|---|---|
| WorkspaceId and resource generation | Kernel/workspace resource identity and current recovered namespace. |
| Workspace binding ID and admission version | S2a binding authority; closing one binding does not invalidate a sibling binding or bump the shared resource generation. |
| Execution authorization reference and version | Authorization owner; single-user execution has an explicit grant too. Area execution references its accepted AreaEnvironmentBinding. |
| Provider registration and qualification identity | Provider owner; exact executable/profile/platform contract. |
| ExecutionId and executor boot identity | S2a execution incarnation and immutable executor receipt; a stable session/card/terminal alias is not process identity. |
| Install epoch | Source installation observed for this execution. Not part of persistent WorkspaceRef. |

A persistent provider-session record binds WorkspaceRef, workspace binding,
execution authorization, scoped ProviderStateId and the native session/thread ID.
It does not treat a persisted generation as permission to restart. Runtime
receipts separately retain the exact generation/epoch/ExecutionId for audit,
deduplication and reconciliation. Truth owns durable intents, bindings and CAS;
provider maps protocol facts; the executor journal owns actual fork/drain facts.

Different execution instances do not share a service, mutable home or native
thread, even if they show the same cwd. Reattachment to the same still-live
ExecutionId may reuse its service after capability validation. A restarted
service gets a new ExecutionId through S2a alias handoff; it does not revive an
old receipt or change an unrelated resource's generation.

## Filesystem and process scope

Kernel supplies an authorized LaunchHandle and typed ProviderLaunchPlan. The
plan contains the registered executable identity, protocol/auth profile IDs,
relative cwd, scoped state/artifact capabilities, explicit environment inputs
and the single-use launch ticket. No arbitrary host cwd, namespace PID/path,
operator HOME, inherited environment or generic file descriptor enters it.

Workspace/supervisor consumes the ticket under the existing lifecycle fence
before actual fork. It joins the owned view, checks directory/namespace identity,
maps the real uid/gid and starts a trusted scope init plus the provider service.
The scope init and its journal are executor mechanisms, not another kernel
lifecycle manager. Namespace handles are controlled capabilities from S2b.

All service project operations see the same view: instruction discovery, config
and trust, Git metadata and snapshots, local execution, file/search/watch APIs,
code-mode/MCP helpers, hooks, shell snapshots and automatic discovery helpers.
No service thread may perform a project read in a host-only helper. Git roots,
common directories and alternates follow S2b private-metadata rules. Unsupported
external gitdirs and root-external view cwd are rejected, including on resume.

The outer mount plan is an explicit typed allowlist: this workspace view,
required system/runtime files, this execution's private provider state,
authorized credential inputs and narrowly scoped IPC/artifacts. It does not
mount the kernel data directory, global object store, another Area's state,
other provider homes, SSH agents, host credential stores or the real source
checkout as an alternate writable route. WorkspaceContent, KernelArtifact and
SourceGitAdmin remain separate; an artifact capability cannot authorize a
project read. SourceGitAdmin never runs provider/repository code.

Every service/child state or credential input is declared by a registered typed
profile with recipient, purpose, access mode and lifetime. Tool sandboxes inherit
the provider's repository-external policy but cannot widen the outer mount plan
or add undeclared inputs. Full-permission modes are qualified separately and
remain Unsupported if they defeat these bounds. Closing inherited descriptors
and hiding host process/control endpoints are launcher contract checks, not
claims made from an environment allowlist alone.

Calls delegated outside the process namespace, including kernel MCP actions,
must consume a scope-bound capability and register their execution/in-flight
occupancy with the same kernel resource facts. A host helper or remote executor
that cannot participate cannot be used by a Supported profile. Network/ports and
external side effects retain the parent policy; this is not network isolation.

## Mutable state and authentication inputs

Provider allocates a private ProviderStateId for the logical session and frozen
workspace/authorization binding, with one live writer. CODEX_HOME/HOME/cache,
transcripts, project trust/approvals, plugins, shell state and temporary files
are scoped there by a typed layout owned by provider. Exact provider-internal
file locations come from the qualified binary/official contract, not kernel
path guesses. No recursive import of an operator home or the existing shared
Codex home is allowed. Desired configuration is a validated projection of the
explicit provider profile, not a copy with a few dangerous keys removed.

State is stable across authorized restarts of that session, not across Areas or
authorization-binding changes. An install-epoch change invalidates in-memory
state and creates a new service execution before resume. Binding changes require
an explicit authorization-owner migration or a fresh session; transcript/trust
state is never silently adopted under a new identity. State storage is a scoped
resource reference retained by S3 lifecycle, not an independent retention policy.

Authentication is a separate required BindingCredentialGrant. It names the
authorization/account owner, permitted recipient/surface, credential profile,
scope and version; secrets have no Debug/log/wire-event representation. A shared
inference account is usable only when that same frozen execution authorization
explicitly grants it. Message authors, request headers and member-specific
HOME/config cannot supply the missing identity. Git/terminal/plugin authority
does not follow from an inference credential.

The first auth profile is **ScopedNativeLogin**: the authorization owner
provisions this private provider state through the binary's public native login
contract. It shares no mutable credential store with another scope and does
not import credentials from private file-layout guesses. It must have an explicit
grant for any credential surface available to the service or its tools; do not
claim service-only secrecy from another same-uid process without a proved
process/read boundary. If that profile cannot satisfy the declared exposure
and refresh contract on the deployment, authentication is Unsupported.
For Codex this profile fixes the official `cli_auth_credentials_store = "file"`
mode in its private scoped home before native login, with exact-binary checks
that it neither uses a shared keyring nor falls back to another home. An
unsupported mode is refusal, not permission to use the operator's default store.

A shared-credential input projection is an independently registered auth
profile, initially Unsupported, not an implicit behavior of ScopedNativeLogin.
It requires a public version-permitted auth exchange, declared refresh and
revocation ownership, and proof that it exposes only the granted inputs.
No new OAuth broker, recursive auth copy or global keychain mount is assumed.
The common kernel sees grant/capability IDs; provider owns external auth encoding.

This version distinction is material: 0.159.2's generated LoginAccountParams
marks chatgptAuthTokens **internal use only, do not use**. The current official
page describes an experimental public flow, but it cannot authorize that old
binary. Native/public login modes must match the exact deployment schema.
[Official authentication protocol](https://learn.chatgpt.com/docs/app-server#authentication)
and [credential-store configuration](https://learn.chatgpt.com/docs/config-file/config-reference)
are reference contracts, not evidence that this deployment has qualified a profile.

## Registration and runtime state machine

The kernel registers a **local runtime scope**, not an upstream environment ID.
Its opaque ProviderRuntimeHandle binds the complete runtime key, executor
receipt, endpoint identity and qualification. Only this handle reaches a caller;
a socket filename or native thread ID is not a capability. Default Codex local
environment access is inside the scope; initial S4 sends no remote environments
override. A future remote-executor profile is a separate qualification and must
not be silently selected when local startup fails.

| State | Allowed transition and required evidence |
|---|---|
| Preparing | Persist runtime/state intent and scope references; validate exact binding, grant, qualification and source epoch; mint S2a ticket. |
| Starting | Executor consumes ticket and journals scope/service identity before acknowledgment. Pending/unknown fork retains occupancy. |
| Provisioning | Verified initialize permits only bootstrap auth/config controls under the explicit provisioning capability; no model/project execution is admitted. Native login may require the authorization owner; cancellation still drains the occupied scope. |
| Ready | Scope receipt verified; official initialize handshake succeeded; required native account/config/profile state validated; endpoint tied to ExecutionId. Only then publish runtime-handle readiness. |
| Disconnected | Immediately stop new request issuance and keep execution/in-flight references. Transport failure is not exit, drain or permission to replace. |
| Quiescing | Stop new work and close mutating admission; reconcile pending requests/tickets, execute authorized stop controls and collect full scope drain. |
| Drained | Executor receipt proves no process/helper/delegated call can act. Acknowledge journal and release active execution references; state may remain retained. |
| RecoveryRequired | Identity, source epoch, state integrity, launch or exit facts are unknown. Remain closed/Busy; never create an empty replacement home or assume NoChild. |

An exact launch retry returns its original immutable execution receipt. A
replacement starts only after old-execution drain/no-child and alias-slot CAS;
reply loss replays that intent, not another spawn. Provider readiness waits,
client disconnects and canceled requests do not release the launch/run permit.

New thread: validate the full handle and binding, persist native-session intent,
send production-owned thread/start encoding, then durably bind the returned ID
before exposing it. Unknown completion is reconciled or requires recovery; do
not make another authoritative thread just because a response timed out.

Each turn, steer, injected input, shell/command request and request that may
read/change project state consumes a fresh kernel operation permit under the
same binding/generation/epoch fence. A run lease remains held while the service,
tools or helpers can act. A turn result is not a resource-idle certificate.

Resume/restart: revalidate the frozen session's workspace/authorization binding
and state reference, reconcile the old exact execution, then register a new
local scope and complete readiness before official thread/resume. Do not pass
an invented environments field, reuse a different workspace's thread, edit
provider-private rollout files, or default to the shared daemon. A native session
that cannot be resumed through the qualified public protocol returns recovery
required; a separately authorized new session is an explicit operation.

Reattach after a control-channel interruption first verifies the exact live
receipt, endpoint, current admission/epoch and exclusive state owner. It cannot
adopt by PID, alias, cwd or thread ID alone. If the original service still lives,
reconnect only to it; otherwise use the drained restart path. Native automatic
recovery never authorizes a new kernel generation or silently changes a binding.

S3's effect owner classifies an operation before choosing the drain protocol
below. A proven same-source Git execution projection does not change source
epoch and does not drain the provider awaiting its result. Actual source
installation, source-environment replacement, archive/reclaim and destructive
lifecycle work require the corresponding positive scope drain. No adapter can
choose that classification from a tool name, an existing lease or a Busy result.

## S3 effect-owner seam and synchronous self-calls

This is an exact interface recommendation to the S3 owner, not a second S4
implementation of installation semantics. S3/workspace returns one sealed typed
plan: `ProvenSameSourceProjection` or `SourceInstallPlan`. Only that owner can
construct the proof and effect footprint; plugins, provider and UI cannot set
an unchecked classification flag. The S3 documents must adopt the same contract
before implementation; S4 does not independently redefine their epoch field.

| Plan | Required invariant and permitted effects |
|---|---|
| ProvenSameSourceProjection | Working source bytes, modes, symlink targets, tracked/nonignored classification, normalization/ignore/config rules, effective source permissions and mount/root identity are unchanged. Only enumerated kernel-owned Git execution metadata (private HEAD/index, owned refs) and ledger/baseline bookkeeping may advance. Source epoch and resource generation remain unchanged; a separate projection/baseline sequence advances. |
| SourceInstallPlan | Any source/environment invariant above changes, or equality cannot be proved. Uses frozen target working-byte manifest, expected before-state, target epoch and S3 intent/receipt recovery. No same-source fallback after a partial source effect. |

Normalized tree equality alone is insufficient for the first variant. The proof
binds S3's raw MaterializedSource and normalized closure, rule identity, resource,
binding/version, source epoch, expected metadata sequence and exact Git admin
handles/expected values. Reclassifying D/W ownership counts as same-source only
when the backend proves it changes none of the visible source/environment
invariants; copy-up, remount, refreshed live lower or source materialization is
the source-install variant even if normalized tree hashes match.

Execute the first variant through S3's existing operation/owner reservation and
private-Git serialization/CAS, with a persisted effect intent before changes.
It grants no new source-writing permission and excludes no unrelated writer
from snapshot, verification or task-admission checks. A waiting provider scope
and the MCP request are retained as live occupancy; they are not falsely marked
Drained or removed from destructive quiescence. The projection simply does not
require resource-wide source-install quiescence. Unexpected Git/source facts
produce Busy/recovery through the owner, never a broad bypass of those checks.

Thus a worker's gate call can capture a valid Revision, pin C, project owned
HEAD/index, run the S3 immutable verification environment and return finished
or running through its original request. Planner commit can settle the same
immutable C and baseline bookkeeping and return its receipt through Services.
Both leave source epoch unchanged when the owner proves the first variant;
neither handler is an exception named in a generic layer. Snapshot stability
and the gate's immutable-source proof remain S3 requirements. If subsequent
edits differ from the accepted Revision, that gate cannot verify a later tree.

After a lost response/crash, the same operation/idempotency key and expected
projection sequence recover the pinned C, partial HEAD/index effects and ledger
settlement exactly once. The caller obtains the original result; it cannot
invent another commit or reconstruct success from status-clean. Provider
qualification must also prove Git/ghost/snapshot caches remain correct after
this permitted metadata change or refresh them through qualified public
protocol. Unchanged source epoch alone does not certify those caches.

The precise S3 amendment is to replace the unconditional rule that even a
no-byte `install_delivered` requires a new epoch: require a durable receipt for
both variants, advance projection/baseline sequence for the proven first variant,
and advance source epoch only for the second. Route run checkpoint, Planner
settlement, lease projection restore, catch-up and recovery through this one
owner classification. This is effect classification, not a per-caller list or
permission for a lease owner to exempt itself from drain.

## Actual source-install handoff and continuation

A source-install operation originating in a provider call must not leave that
native call waiting for an installation which requires its own scope to drain.
Use the following durable operation protocol for every such effect, independent
of the API/tool name. Calls outside a provider scope use the same source plan
and receipts without the native-call continuation.

1. Under the existing fences, persist the source plan and continuation intent:
   operation/input digest, frozen source/target manifests and expected epoch,
   originating exact ExecutionId/native call, persistent session/state and
   workspace/authorization binding, and a monotonically checked handoff ID.
   Pin both S3 content closures before any effect. The durable operation owns
   continuation/replay; the native request does not own an install wait.
2. Durably settle the original call to an Accepted operation receipt and end
   its handler/dispatch. The typed Services/MCP result conveys that receipt;
   it never falsely reports installed/committed. Record native response outcome
   as delivered or unknown. Response loss does not undo acceptance, and no new
   source effect is allowed while that original call/delegation is unfinished.
   The handler must not synchronously await the continuation it just created.
3. Seal new work, interrupt/stop the identified native execution through its
   lifecycle capability, finish or cancel the original native request using
   qualified protocol, and positively drain its service, tools, helpers and
   delegated calls. A durable handler result alone is insufficient when an old
   live invocation still waits. Unknown/unfinished calls remain Busy; do not
   clear their references to break the wait. No source install occurs before
   this stage completes. Any extra old-generation work before drain is checked
   against the frozen before-state and cannot silently change the target plan.
4. S3 performs/replays that one frozen install and commits its epoch/receipt.
   Reconcile partial paths, HEAD/index and DB using the same intent; never pick
   a new target on retry. Only then may alias handoff allocate a new ExecutionId,
   register/readiness-check a new scope and resume the authorized native session.
5. The resumed harness receives a fresh continuation/result-read capability
   after revalidating the frozen binding and current access. It observes the
   original operation result and supplies it through the public native input
   protocol as an explicit kernel continuation, not a forged response from the
   old execution. Console observation shows the accepted operation and its
   eventual result while the worker/Planner resumes normal interaction.

Crash/reply-loss replay inspects these durable stages. Acceptance with unknown
response resumes drain/reconciliation, not another native call; drained but
uninstalled resumes the same S3 plan; installed but unregistered creates one
new execution by alias CAS; result delivery retries the same handoff/result
identity without repeating installation. Old credentials, queued calls and
result consumers never upgrade to the new incarnation. Cancellation/revocation
follows the authorization owner's accepted-operation policy; a new grant is
not substituted. If public native resume cannot reconcile an interrupted or
unknown tool call, require recovery rather than edit private history. These
normal and failure continuations need production no-model contract coverage.

Idle services may be closed for a true installation idle point, retaining their
authorized native state. Busy terminals/helpers may postpone it indefinitely.
New-epoch runtime handles are published only after the installation receipt;
no service with a stale source/config environment is treated as ready for it.

## One capability envelope for all control

The common dispatcher accepts ExecutionControl carrying the S2a exact-execution
capability plus a provider operation. It validates workspace binding, execution
authorization, ExecutionId/receipt, generation, epoch, operation purpose and
admission before protocol encoding. Direct process handles use the same identity.
An old control never resolves an alias to its new execution incarnation.

This covers observations/subscriptions, input, steering, approvals and server
requests, configuration/account operations, session administration, filesystem
and search RPCs, stdin, resize, signals and cleanup. New protocol operations
must declare their typed authority in the provider-owned dispatcher; unknown
methods fail closed. There is no raw user-accessible JSON-RPC tunnel and no
hand-maintained handler/file/test-name allowlist that can omit future controls.

Read-only observation requires a narrower authorized artifact/session view;
source-content reads still require WorkspaceContent authority. Account/config
data is redacted at its owner. After admission closes, lifecycle control can
stop/drain the identified old execution but cannot inject input or start work.
Historical logs/terminal receipts are read through authorized frozen artifacts,
without issuing a live RPC or rebinding the old receipt to a current execution.
Approval responses and late tool replies retain the originating request,
execution and frozen authorization, rather than using the current message author.

## Managed view-worker console and endpoint isolation

The first view profile returns a typed `ManagedWorkerConsole` capability from
provider preparation. Generic terminal/UI code renders its declared observation,
input, approval, stop and operation-result ports; it does not branch on Codex or
application names. An ordinary worktree profile retains its existing native
terminal capability. View creation/start therefore still has a functional
worker interaction path, rather than refusing the normal terminal entry point.

The managed console streams authorized worker/tool output, gate/commit and
continuation results. A submitted message requests a new/continued turn through
kernel admission; approval responses bind their exact execution/request; stop
uses lifecycle control. Every submission is a fresh typed ExecutionControl,
not raw PTY keystrokes or bytes written to app-server stdin. Provider exclusively
encodes/fragments JSON-RPC. Native slash commands, native session/account
management and the `codex resume --remote` screen are not this view console.
This changes presentation and native-only affordances, while preserving worker
turn/approve/stop/observe actions. Worktree native TUI behavior is unchanged.

The view app-server is launched with official `--listen stdio://`, connected
only by supervisor-owned anonymous pipes to the trusted provider dispatcher.
There is no raw TCP/UDS listener, published remote URI or upstream bearer token
for a view console/native client. Native remote CLI clients receive no endpoint
or native-client grant. The existing URI persistence and resume/restart command
builders must consume the typed console attachment and cannot run the worktree
native attachment against a view runtime. No second gateway is introduced.

Anonymous pipes alone are not isolation from same-uid tools: repository tools
must run in their own nested PID/proc and mount boundary, seeing no service or
host /proc and no provider-control/state paths. They inherit only declared tool
FDs, not service-control pipes or private provider HOME. Trusted service helpers
may receive only their registered typed inputs, not a general descriptor bundle.
The qualified local-tool sandbox/launcher must enforce this boundary, including
proc-fd and symlink access, and prevent alternate app-server/control listeners.
No claim follows merely from hiding a URL, a mode-0600 socket, a private pathname
or matching uid. A native binary/profile that cannot enforce this boundary is
not qualified; launching one after checking a grant once is not a substitute.

Console connections bind the exact execution and terminal/session attachment.
Revocation seals its work ports and rejects queued/late turn, config, approval
and input requests before upstream write; authorized historical results remain
artifact observations. A request already sent is tracked in flight until its
outcome or positive drain, not retroactively claimed canceled. On replacement,
old connections close; an authorized fresh attachment obtains new capabilities.
Unsent old frames are never retargeted to a new ExecutionId. Concurrent revoke
and dispatch linearize on the same admission fence and durable in-flight record.

The console is a browser/kernel presentation, not a native CLI process with
its own credential cache or untracked PTY. Any renderer/helper that actually
accesses the workspace is a registered execution in scope and participates in
drain. Ordinary separately authorized terminals retain their own S2a scope and
may still keep resource quiescence Busy. A malicious native client in such a
terminal cannot attach to the managed service by guessing a socket or opening
its parent FDs, because that service endpoint/proc/state namespace is absent.

## Positive service/tool/helper drain

Use one S2a execution scope whose trusted init remains alive independently of
the provider leader, inside a private PID namespace. It adopts/reaps orphaned
descendants, including nested PID namespaces and setsid/background processes.
No unregistered external process may spawn into the scope. Scope creation and
delegated-execution registration are serialized with ticket revoke/close.
Process groups alone are insufficient; observed Git helpers are a regression
fixture, not an exclusion from ownership.

Drain closes new request/fork/delegation entry points, resolves pending tickets
and in-flight native/tool/MCP calls, then performs authorized graceful stop of
known executions. The trusted init confirms no descendant remains and exits;
the executor verifies scope/init identity and final namespace/process evidence
before journaling Drained. A process that can still fork keeps the scope live.
Unknown identity, helper liveness, lost scope journal, stuck RPC or failed
graceful stop remains Busy/RecoveryRequired. No timeout, leader exit, DB idle,
empty upstream terminal list or websocket close substitutes for that receipt.
Closing registered launch admission does not intercept arbitrary forks inside
an upstream service: while any such process lives, it can create descendants
and the scope is still live. The trusted init's eventual empty-scope proof is
required even after all registered request queues report empty.

Do not kill an unknown process or destroy its namespace to manufacture drain.
The parent no-force-kill policy remains. An explicit authorized stop action may
target a proven owned execution; any escalation is owned by existing lifecycle
policy, not a new provider timeout rule. Scope init is not terminated merely to
exploit the PID namespace's destructive exit behavior. Recovery reconciles every
old scope before a new state writer, generation or destructive operation opens.

## Area common authorization and content access

Area members use the same Track WorkspaceRef. Provider state/runtime partition
follows the granted AreaEnvironmentBinding and its version, not message authors.
The collaboration authorization owner decides grant acceptance/revocation and
accepted-batch policy. Kernel verifies it for every new admission, restart,
reattach, content operation and lifecycle action. Provider consumes an already
authorized plan, never interprets membership or selects a member's credentials.

The persistent turn/session fixes both workspace and common-execution grant.
Configuration, instructions, Git, attachment and search reads consume that same
authorized content context. A caller authorized only to read an Area cannot
create a runtime, answer its approvals or acquire its stdin. Sharing a native
account does not grant access to another Area or kernel object directory.
Revoking one binding seals its runtimes only; resource-wide destruction still
requires all S2a bindings/executions and S3 references to permit it.

## Qualification registration and local providers

Provider registers a typed execution profile with its protocol encoder, state
and auth profile, allowed input manifest, sandbox/control scope and qualification
requirements. `ViewSupport` is Supported only for an exact qualification key:
executable/package digest/version (including launched provider helpers),
protocol/profile digest, launch/supervisor platform
contract, auth/state contract and relevant effective configuration digest.
Certificates record actual positive and negative contract results. Missing,
stale, skipped or differently configured evidence means Unsupported; a boolean
configured by an adapter cannot grant qualification.

Qualification explicitly covers config/AGENTS and imports, trust/approvals,
Git/common-dir facts, ghost/snapshot/undo, all filesystem/search/watch paths,
session state, tools/helpers and restart/drain. A feature may be disabled only
by a version-permitted mechanism whose production encoding and negative test
