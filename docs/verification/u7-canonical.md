## Ownership and boundaries

REST creation extends `creation_plan.rs` and `dormant.rs` in place. Immutable receipts decide before mutable selection/preparation. Existing preparation admits the template/plugin/input; allocation reads recipe revision and captures the forked Report in its transaction. Canonical allocation freezes material into a protected Planner card field. Truth includes that Context in the first submission's immutable render plan, in the claim transaction; subsequent turns and cold recovery reuse their original plan rather than mutable sources. Human authorship remains separate.

Historical `human_source` checks private execution authority; a canonical Report copy requires Collaborate content access. These are different contracts. Canonical source admission now lives at allocation's existing fork read and uses the shared organization access owner; the extra dormant source query was removed. No execution grants, authors, pending queues or native identities are copied.

Canonical preparation receives the transaction-admitted Area kind through the original preparation owner. It does not lease read-pool capacity while holding the writer. Existing historical preparation keeps its lookup and error ordering. Plugin template resolution only snapshots the synchronous host table/registry and does not acquire a database writer or perform plugin RPCs.

The Planner instruction entry suppresses duplicate template/input injection only when the canonical creation field is present. All production callers were inspected: `harness/instructions.rs` routes Assistant through its separate profile branch. Claude named-source shapes remain explicitly historical, without runtime fallback. The existing blank predicate is preserved; `accepts_unavailable_blank_track` was already absent in the recovery baseline, and was neither renamed nor replaced.

No changes to factory, Assistant creation, track-conversation routes, Claude/ACP planner implementations, migrations, attached/cwd/admin/cross-area admission, or handwritten frontend code. #3037 was inspected and remains separate. The generated OpenAPI refusal documentation is synchronized from the CardPatch owner and carries an explicit ownership trailer.
