# Shared Markdown and math

Outcome: report prose and assistant replies use one Markdown parser and one generic renderer, with inline and display TeX rendered in both. Preserve report outline anchors, reference recognition, workspace and external image policies, contextual navigation, literal user messages, copy, narrow layouts and live replies. Exercise real report and chat entry points with formulas, code fences, navigation, images and streamed updates.

Review tier: L2: the migration changes a large shared rendering surface, including handling of untrusted content. Review security and URL admission, caller-specific behavior, syntax compatibility, architecture and performance.

Owner change request: extend the frozen `core/markdown` AST with inline and block math, and add the math parser dependencies to the package manifest and lockfile. Register a generic Markdown UI primitive in the frozen module inventory; load KaTeX's vendor stylesheet in the styles vendor entry. The shared renderer consumes sanitized syntax, with typed rendering callbacks for caller-owned links, images, heading styles and anchors. Report preparation remains the owner of outline, context and navigation; chat retains its own image and navigation policies. The UI layer's core type restriction requires an explicit narrow exception for the generic Markdown AST, whose types carry syntax rather than business-domain data. Orchestrator decision: accept this scoped request. No generic layer may assume a specific feature or Track.

Keep TeX rendering non-trusting, bound expensive expansion, preserve malformed formulas as readable source, and do not interpret formulas inside code. Confirm math behavior and currency/escaping edge cases, long replies, raw HTML handling, and both desktop and narrow browser layouts. Adding another normal Markdown consumer should require no permanent registration beyond importing the shared public component.

The two narrow dependency rules run once in the frontend lint job. Their positive and negative fixtures run with the automatically discovered architecture test in one unit-test shard. Adding a Markdown node changes the core vocabulary and the shared renderer's exhaustive handling; it requires no new filename, feature or test registration in these rules. Changing the UI/core boundary requires updating the rule and its corresponding fixtures.
