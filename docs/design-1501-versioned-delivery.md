# Planner 多文件交付与验收接续

状态：实现方向与验收约束；未完成项不代表已经实现。
基线：`a3266c55b4a753ba09ec2c73413787aca36509d4`，2026-09-08。
对应 #1501、#1492；承接[任务连续性框架](architecture/1501-task-continuity.md)
与[Planner 实施总纲](design-1501-planner-contract-roadmap.md)。

## 1. 要交付的体验

用户要求代码、README、测试和复核报告作为一组可追溯的成果交接。
Planner 声明业务输出、验收要求和依赖用途；系统负责封存真实文件、确定验证
对象和准备输入。用户无需手动搬运工作目录，Planner 无需拼接 hash 或临时路径。

完成任务执行、保存成果、通过验收、允许下游使用分别记录。某一项成功不冒充
其他项成功。失败时保留有用成果和具体问题，后续在该版本上修复并重新验收。

本轮首先做一个小项目的闭环，不引入通用发布平台、多仓库合并或全 Provider 改造。

## 2. 已核实的当前行为

- 4140 的 `/api/version` 报告上述后端 SHA；前端资源未独立映射到提交。
- 普通 gate 默认使用绑定 Worker 工作区；绑定缺失不会悄悄回退 Track 根目录。
  显式 `gate.cwd` 仍优先。旧实验的错误目录不构成本次的新复现。
- 普通 `FrozenVerify` 固定 task、gate attempt、cwd 和 gate，没有不可变候选 ID。
- #1581 支持隔离 Codex 的一个 JSON 文件交付；验证读取封存字节，但只验证 JSON
  语法。该选择明确拒绝普通 gate，与普通验证流程是两条独立路径。
- 产物库已有多文件 Git 快照和完整候选物化。非 Git 隔离工作区当前只有单文件
  FD 捕获入口；不能为了复用 Git 路径伪造 `.git`，也不能无差别扫描私有目录。
- `materialize_candidate` 只有库和测试调用。现有恢复继承原输入，不自动继承
  失败输出。已 Done 而 publication 失败的生产者不满足现有 Failed 恢复前提。
- accepted-report 证明报告来自哪次执行，没有要求复核报告绑定被复核版本。
  普通历史 run 的结果和文件引用仍可读取，不应误称普通文档交接完全缺失。

## 3. 三个精确对象

这里定义职责和关系，不要求为每个对象单独建表；物理映射随切片决定。

**候选成果 C1** 是一组封存的真实文件，至少能覆盖代码、README 和测试。
清单记录规范化相对路径、字节内容身份、长度和受支持的执行位；来源 attempt、
冻结契约和停止证明通过内核记录关联。内容 hash 不单独证明来源或授权。

**验证证据 E1** 指向准确的 C1，并记录所依据的冻结验收要求、实际执行身份、
检查范围、结果和证据入口。机器 gate 和语义复核分别保留其权威，不互相替代。
仅报告通过验收，不意味着其中讨论的实现已经通过验收。

**交付记录 D1** 绑定 C1、满足所需策略的证据及现有验收决定。对用户可以表现为
同一版本下的一组文件和报告。不能引入另一个可独立修改的 accepted 位。

JSON 可以是系统生成的清单或引用入口；它不是把源码编码进去后交给模型重建。
下游取得实际封存字节。普通文件与报告可以共同呈现，不要求额外开发下载打包功能。

复核报告产生于检查 C1 之后，因此报告作为证据引用 C1。不能把报告写回 C1 后
继续使用原版本身份。若需求要求报告也属于可执行候选内容，则其加入形成新候选，
需按冻结策略重新检查。初版采用候选与证据分别封存、交付时关联的路径。

## 4. 首个可用闭环

1. 作者声明一个有界文件集合和公开的交付要求；私有 gate 不得额外发明必需文件。
2. 隔离执行者产出文件并报告。内核确认准确执行已停止写入后封存 C1。
3. 验证者取得由内核物化的 C1。gate 的执行根和 Reviewer 的输入来源都绑定 C1；
   不读生产者可变目录，不从分支名或“最新”解析替代版本。
4. 机器结果和复核证据绑定 C1。存在未决阻塞问题时，成果可查看或供授权修复，
   普通交付资格仍被阻止。
5. 满足合同要求后，普通消费者 claim 原子固定 C1 和资格依据。Operation 准备
   输入并核验后才开始执行。生产者目录修改、删除或出现后续版本不替换已有绑定。
6. Planner 能从已有计划/结果读面知道交付包含什么、验证什么、哪里未通过和
   下游实际接收什么；不要求额外创建纯文件搬运业务节点。

只接一个生产者、一份文件集合、一种隔离执行环境、一套明确 gate、一名 Reviewer
和一个普通消费者。gate 是业务验证节点或已有验证机制，不以 transport 节点替代。
普通顺序 `depends_on` 的原义保留，文件输入必须明确用途和输出选择。

### 文件与验证边界

初版优先声明有界普通文件路径集合，复用 FD 捕获与已有原子快照事务。
不递归扫描未知目录，不允许符号链接、硬链接、特殊文件、跨挂载或私有路径。
集合、父目录和累计字节均受资源上限约束；缺必需文件时不得发布完整可交付成果。
未列入合同的文件不冒充已交付内容。更动态的目录声明属于 follow-up。

机器执行复用已有 gate 的进程所有权、环境白名单、退出结果和 Operation 恢复能力。
不能在 publication 内另写不可恢复的 shell subprocess，也不能为了验证而放宽
终态任务重新开工的守卫。

接入方向选择封存后的独立 `candidate-verify` Operation。producer 保持现有无
普通 gate 的隔离执行及 Done 后封存；验证操作固定 C1 和验收策略，复用抽出的
现有 gate 进程执行机制，在自己的工作副本执行真实检查。不新增 TaskKind、
不启动空 Worker，也不使用占位 Terminal 任务。该模式拒绝外部 `gate.cwd`。

该 Operation 必须完整记录准备、物化、发布执行与完成事实：精确候选和冻结策略、
当前授权、操作租约、release 前已记录的进程身份、退出/重启恢复和有界并发。
验证证据写入 Operation 结果，不改写 producer 的 Task 状态或 gate 状态；
Done 后的验证权限不构成再次启动 Worker 的权限。声明与持久化映射在 A1 编码前
确定，不能用缺省候选 ID 解释旧验证。
现有 host gate 的环境白名单不构成文件系统隔离。A1 沿用已有 gate 的受信执行
权限和边界，不宣称能够安全运行恶意 verifier；封存对象不得提供给 gate 作为
可写工作根。若验收要求防范主动越界写入，则必须另行接入明确隔离的 launcher，
不能仅靠 cwd 或只读约定声称满足。

A2 的 Reviewer 从验证 Operation 已固定的输入关系取得 C1，不重新选择 producer 的
最新版本。其结构化复核结果须明确是否通过及未决阻塞问题，subject 由内核输入
绑定和报告来源推导。扩展现有 Planner verdict 写入链与 consumer claim 校验，
要求 gate、复核、冻结策略、候选全部匹配，并记录精确证据；不得新建可独立改写
的验收真源。A1 只支持机器验收策略，不能把要求复核的合同降级为机器通过。

验证者需要写构建缓存时使用自己的工作副本，封存源不暴露写入。
检查起点绑定 C1 不等于运行期间工作副本不可变；验证策略必须说明实际检查范围。
若构建产物是最终交付内容，它必须成为明确的新产物并获得相应验证，不能偷换 C1。
初版不复用不同版本的验证结果；零测试退出成功不得被描述为测试覆盖通过。

## 5. 后续修复闭环

1. 失败/拒收记录保留准确 C1、原输入、原契约和具体问题，不改写历史结果。
2. Planner 明确选择修复。确定性层绑定它已观察的候选和问题，现有授权规则在
   事务内复查；旧决定不得被重定向到更新的执行或候选。
3. 新 attempt 按修复用途获得 C1、原始输入和修复提示。修复用途不授予正常发布
   权限，也不要求把旧失败临时改成 accepted。
4. 停止后封存 C2；对 C2 重新执行所需 gate 和复核。每个阻塞问题必须有可核对的
   解决依据或授权处置，不能因修复任务完成而自动关闭。
5. 只有 C2 的匹配证据满足原验收要求后才可交付；已绑定 C1 的旧消费者不静默更新。

如果改变目标或验收要求，走明确契约变更，不能作为原合同修复偷偷实施。
已有失败恢复和 publication 失败是不同状态；必须显式设计后者的候选修复入口，
不能简单删除 Failed 守卫。实现顺序保留该区别。

失败发生在报告之前时，在可证明停止后保存有用候选；不能安全取得快照时明确
记录“没有可信候选”。停止未知不推导停止，也不承诺完整断点恢复。

## 6. 实施与验收账本

只有一个当前产品切片；库级前置工作合入该产品切片，不独立宣称交付体验完成。

- [x] A1：多文件候选 → 真实同版本 gate → 明确机器验收策略 → 下游精确接收。
  [#1584](https://github.com/keanji-x/neige-calm/pull/1584) 已合入；
  [实际实现与验收记录](design-1501-candidate-verification.md)说明范围和限制。
  采用上述 candidate-verify Operation；声明与持久化映射已在实现文档记录。
  要求 Reviewer 的合同在 A2 前明确不支持，不作为机器通过的同义词。
- [x] A2：同版本 Reviewer → 问题与结构化复核 → 现有验收事务校验全部证据 →
  下游精确接收。[实现与本地验收记录](design-1501-candidate-review.md)包含真实三任务
  演练、可靠结束通知和精确决定绑定；发布仍遵循双路复审及 CI 门禁。
  初版 Reviewer 等待机器检查通过，拒收候选的修复仍属于 B。
- [ ] B：保留被拒候选/问题 → 一次显式修复 → 新候选重新验收 → 精确交付。
  不并发铺开通用恢复、计划编辑、全局 Finding 或 Provider 重构。

每个产品切片需要生产入口回归、两路独立完整复审、相关 gates 和 CI。
真实演练采用小项目和有界任务，记录版本、节点、介入和最终字节证据；4140 现有
任务不改动，不重启共享服务，不运行共享主机真实 Tier2 E2E。

关键验收：

- 同一交付包含源码、README、测试，Reviewer/gate/消费者的来源候选可核对相等。
- 修改或删除生产者目录不改变已封存输入；损坏快照、准备冲突或撤权时不启动。
- gate 错误、复核未决问题、报告被接受与代码可交付分别呈现。
- 同一操作重放不创建新版本；原合同改变或迟到旧结果不能污染当前决定。
- 修复保留原文件与问题，新版本不能使用旧版本的通过结果。
- 无额外纯搬运节点；Planner 不提供内部版本 ID、工作区路径或 hash。

对精确版本/启动围栏等关键断言做有预测完整红集的生产 mutation，再安全恢复。
普通 UI 文案不机械增加 mutation。文件类型、格式验证不声称业务验收。
